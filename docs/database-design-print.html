Database Engineering Assignment / MySQL 8

BookMyShow Ticketing

Normalized theatre, showtime, seat inventory, timed holds, bookings, payments, and webhook idempotency.

Submission document | MySQL 8.0.16+ | Timestamps stored in UTC

Design boundary: InnoDB is the authority for seat ownership. Redis may accelerate availability hints, but a Redis key alone never confirms a hold or booking.

Normalization

  • 1NF: Attributes are scalar; seat selections are rows, not lists stored on a booking.
  • 2NF: Descriptive values depend on their full candidate key. Seat and show details are separate from booking-seat records.
  • 3NF: Theatre data lives in theatres; screens reference theatres; showtimes reference screens and movies. No theatre or movie description is copied into a showtime.
  • BCNF: Entity determinants are candidate keys. Inventory uses (showtime, seat); allocations have candidate keys (showtime, seat) and booking_seat_id. booking_seats does not repeat showtime, which is determined by its booking.

Insert/update triggers verify that inventory seats belong to the scheduled screen, booking-seat snapshots exist in the booking's show, and allocation owners match the show and seat. The offered price and the historical price are different facts: future price changes cannot rewrite an existing booking.

Seat Holds and Concurrency

  1. Create a PENDING booking with a UTC expiry, typically five minutes ahead.
  2. Lock the selected show_seats rows using SELECT ... FOR UPDATE, in ascending seat order for multi-seat requests.
  3. Insert a booking_seats price snapshot and then a seat_allocations row. Release any expired allocation in the same transaction before reclaiming it.
  4. Require one inserted allocation per requested seat. The allocation primary key prevents double ownership. If any seat conflicts, roll back the whole transaction.
  5. Store the total from locked inventory prices and commit. Return a successful hold only after commit.

An expiry worker locks the pending booking and its inventory rows, deletes only expired allocation rows still held by that booking, and marks the booking EXPIRED atomically. Booking-seat history remains for auditability.

Expiry and payment race

Expiry and payment confirmation lock the booking and seat inventory in the same order. Payment success is accepted only while the booking is pending, before expiry, and every requested seat still has a matching held allocation. The transaction marks the booking confirmed and allocations booked. If expiry wins, a late successful charge is refunded or compensated; it must not reclaim the seat.

Idempotent Payment Webhooks

  1. Verify provider signature and timestamp before accepting an event.
  2. Insert into payment_webhook_events; unique (provider, provider_event_id) makes retries idempotent.
  3. In one transaction, lock event/payment/booking, validate payment ID, amount, currency, and booking state, then update payment, booking, allocations, and event status.
  4. Dispatch ticket, email, and refund side effects through an outbox or independently idempotent workers.

The payment idempotency key handles retried payment creation. A generated unique successful-booking key permits at most one successful payment per booking while allowing failed attempts.

P2: Shows for Theatre and Date

Convert local midnight and the following local midnight in the theatre's IANA time zone to UTC in the application. Pass those instants as a half-open interval; resolving both boundaries separately handles 23- and 25-hour DST days.

SELECT sh.showtime_id, m.title AS movie_title, m.language_code,
       sc.name AS screen_name, sh.starts_at_utc, sh.ends_at_utc
FROM theatres AS th
JOIN screens AS sc ON sc.theatre_id = th.theatre_id
JOIN showtimes AS sh ON sh.screen_id = sc.screen_id
JOIN movies AS m ON m.movie_id = sh.movie_id
WHERE th.theatre_id = @theatre_id
  AND sh.status = 'SCHEDULED'
  AND sh.starts_at_utc >= @day_start_utc
  AND sh.starts_at_utc < @day_end_utc
ORDER BY sh.starts_at_utc, m.title, sc.name;

Concurrency Test

sql/06_concurrency_test.sql is a two-session check. Run it concurrently in two MySQL clients, setting the test user to 2 in one session and 3 in the other. Both target show 1001, seat 403. One should report one seat acquired; the other should report zero after the conflicting allocation is observed. Reset the fixture seat between runs.

Burst Load Test

The repository contains no running API, so a measured system load result cannot be produced from the SQL-only starter. The k6 script targets the hold API contract and proves the one-winner property once connected to a backend.

k6 run -e BASE_URL=http://localhost:8080 \
  -e SHOW_ID=1001 -e SEAT_ID=403 -e VUS=500 \
  tests/seat-contention.js

Expected contract: POST /v1/holds returns 201 for the single winner and 409 for losing contenders. The test thresholds exactly one successful hold and less than 1% unexpected HTTP failures. Repeat with varied seats and ramped arrivals; record p95/p99 latency, throughput, lock waits, deadlocks, database CPU, Redis pressure, expiry lag, and queue depth. A same-seat burst validates exclusivity, not platform-wide capacity.
